# Packaging and release

This document lists the NuGet packages, explains how versions are derived and describes the release procedure.

## Packages

Fourteen libraries are packed, all with the id `InFine.QuantFinance.<Name>`, the same version, target `net8.0` and are
MIT-licensed. Each one ships the assembly, its XML documentation, a README and an icon, and a `.snupkg` with symbols.
Dependencies on the other packages are the project references; the `Hybridizer.Runtime.CUDAImports` column shows
whether the package references it directly (the others get it transitively when they depend on one that does).

| Package | Content | Depends on (packages of this set) | Hybridizer runtime |
| --- | --- | --- | --- |
| `Arithmetic` | Forward-mode dual numbers `Dual` and `Dual4` | none | no |
| `Scheduling` | Parallel executors, `alignedindex`, reductions | none | yes |
| `Numerics` | Allocation-free numerical kernels (interpolation, discount-curve evaluation), Levenberg-Marquardt, BFGS, Cholesky, eigen-decomposition, nearest correlation matrix | none | no |
| `Random` | MRG32K3A, Philox, scrambled Sobol, Brownian bridge, MKL and cuRAND wrappers | `ClosedForm` | yes |
| `ClosedForm` | Black-Scholes-Merton, Black-76, implied volatility, barrier / Asian / lookback, Heston, Hull-White, multi-asset references | `Arithmetic`, `Numerics`, `Scheduling` | yes |
| `Models` | Diffusion kernels (Black-Scholes-Merton, Heston, correlated log-normal, Hull-White) and their adjoints | `ClosedForm`, `Numerics`, `Scheduling` | yes |
| `Payoffs` | Monte Carlo payoffs (vanillas, Asian, barrier, lookback, baskets, autocallables), pathwise and adjoint Greeks | `Models`, `Scheduling` | yes |
| `LongstaffSchwartz` | Least-squares Monte Carlo for American options | `Models`, `Payoffs`, `Scheduling` | yes |
| `Market` | Dates, calendars, day counters, schedules, curve instruments, yield curves | `Numerics` | no |
| `Volatility` | SVI / SSVI slices and surfaces, arbitrage checks, calibration | `ClosedForm`, `Market`, `Numerics` | via `ClosedForm` |
| `Risk` | Covariance estimators, VaR / ES, Monte Carlo VaR by full revaluation, stress tests | `ClosedForm`, `Numerics`, `Random` | yes |

| `Backtesting` | Backtesting engine, strategies, stationary block bootstrap | `Portfolio`, `Random`, `Risk`, `TimeSeries` | yes |

To use a feature, reference the most specific package: `dotnet add package InFine.QuantFinance.ClosedForm` brings
`Arithmetic`, `Numerics` and `Scheduling` with it.

### Not packed, and why

- Tests, `TestSupport`, benchmarks, tools, samples and `research/`: not libraries.
- `InFine.QuantFinance.Cuda`: its output is the native CUDA satellite, generated on demand with a Hybridizer installation
  (see [gpu.md](gpu.md)). It is not a managed library and cannot be produced on a standard CI runner.
- `InFine.QuantFinance.Excel`: the add-in ships as an `.xll` (see [excel.md](excel.md)), not as a package.
- `InFine.QuantFinance.Excel.Core`: it is the implementation behind the add-in (argument coercion, object cache, `QF.*`
  functions returning error sentinels). Its surface is shaped by Excel, not by .NET callers, and publishing it would
  commit the project to keeping it stable. .NET users call the libraries above directly. It can become packable later;
  add its name to the list below.

A project is packable only if it is listed in `QfPackableProjects` in
[`Directory.Build.props`](../Directory.Build.props); everything else is not packable by default, so a new project never
ships by accident. The shared metadata (authors, licence, URLs, README, icon, tags, symbols, SourceLink, MinVer) is
defined there for the listed projects; each project only sets its own `Description`.

### What a package contains

- `lib/net8.0/<id>.dll` and `<id>.xml` (IntelliSense documentation).
- `README.md` (from [`build/package-readme.md`](../build/package-readme.md)) and `icon.png`
  ([`build/icon.png`](../build/icon.png), generated by `python3 build/make-icon.py`).
- `.nuspec` with the MIT licence expression, repository URL and commit, tags and dependencies.
- In the `.snupkg`: the portable PDB, with SourceLink mapping to `raw.githubusercontent.com` at the exact commit, so a
  debugger downloads the sources of the commit the package was built from.

The CUDA satellite is not part of any package. The packages run on plain .NET; GPU execution needs a satellite built
from the repository with Hybridizer.

### XML documentation

The documentation file is generated for every package. Warnings about documentation that is missing (CS1591, CS1573,
CS1712) are not enforced yet, because many public members have no summary and many methods document only some of their
parameters. Warnings about documentation that is wrong (malformed XML, unknown parameter, unresolvable `cref`) fail the
build. Closing the missing-documentation gap is a follow-up.

## Versioning

Versions come from git tags through [MinVer](https://github.com/adamralph/minver); there is no version number in any
project file.

- The tag prefix is `v`. Tag `v1.15.1` gives version `1.15.1`; `v1.16.0-rc.1` gives the pre-release `1.16.0-rc.1`.
- A commit after the last tag gets the next patch version as a pre-release, `0.1.1-alpha.0.<height>`, where height is the
  number of commits since the tag. Before any tag exists the version is `0.0.0-alpha.0.<height>`.
- All packages share the version. MinVer needs the history and the tags: CI checkouts that pack must use
  `fetch-depth: 0` (the release workflow does). A shallow clone without tags gives a meaningless `0.0.0-alpha.0.<n>`.
- To force a version without tagging (for a local test), pass `-p:MinVerVersionOverride=1.2.3-test`.
- Versions follow [Semantic Versioning](https://semver.org): the major version changes for breaking API changes, the
  minor version for features, the patch version for fixes.
- `ContinuousIntegrationBuild` is switched on by the `GITHUB_ACTIONS` variable, which makes the build deterministic and
  path-independent. A local build does not use it, so a package built on a developer machine is not byte-identical to the
  CI one and should never be published.

## Building packages locally

```sh
dotnet pack QuantFinance.sln -c Release -o artifacts/packages
```

The output is one `.nupkg` and one `.snupkg` per library. Inspect a package with `unzip -l <file>.nupkg`; to try
it from another project, add `artifacts/packages` as a local NuGet source.

## Release procedure

1. On `main`, with CI green, update [`CHANGELOG.md`](../CHANGELOG.md): rename `[Unreleased]` to `[X.Y.Z] - YYYY-MM-DD`
   (add a fresh empty `[Unreleased]` above it) and fix the link references at the bottom. The GitHub Release notes are
   this section.
2. Commit and push the change.
3. Create and push an annotated tag on that commit:

   ```sh
   git tag -a vX.Y.Z -m "InFine.QuantFinance X.Y.Z"
   git push origin vX.Y.Z
   ```

4. The [`release.yml`](../.github/workflows/release.yml) workflow runs on the tag:
   - checks that the tag is a version, restores, builds and tests;
   - packs, and checks that every package carries the tag's version;
   - uploads the packages as a workflow artifact (`packages`);
   - pushes the `.nupkg` and `.snupkg` files to nuget.org with `--skip-duplicate` through
     [NuGet trusted publishing](https://learn.microsoft.com/nuget/nuget-org/trusted-publishing), when the `NUGET_USER`
     repository variable is set; without it the job ends with a notice and pushes nothing;
   - creates the GitHub Release for the tag with the changelog section and the packages attached (a tag with a
     hyphen, such as `v0.2.0-rc.1`, is marked pre-release).
5. Check that the packages appear on nuget.org (indexing takes a few minutes) and that the Release page reads well.

Setup, once (no API key is stored anywhere): on nuget.org, *your profile → Trusted Publishing*, add a policy with
repository owner `infineco`, repository `quant-finance-library`, workflow file `release.yml` and no environment; then set
the repository variable `NUGET_USER` to the nuget.org profile name that owns the policy
(`gh variable set NUGET_USER -R infineco/quant-finance-library`). Each run exchanges the job's GitHub OIDC token for a
one-hour API key. To publish a tag that was released before this setup, start the workflow by hand
(*Actions → Release → Run workflow*, input `v1.15.1`): it builds that tag and pushes it, without touching the GitHub
Release. For a first release the id prefix must be reserved on nuget.org so that the
packages carry the verified-owner mark. A failed run can be re-run: pushes skip versions that already exist; the GitHub
Release step fails if the release exists, so delete the release (not the tag) before re-running that job.

A bad version cannot be replaced on nuget.org: unlist it (nuget.org does not delete) and release a new patch version.
